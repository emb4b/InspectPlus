# Sync Contract

## Purpose

This document defines the backend-to-mobile sync contract for InspectPlus.

It describes:

- the synced entities
- the payload shape of `pull_changes(last_pulled_at)`
- the payload shape of `push_changes(changes)`
- deletion behavior
- conflict behavior
- client responsibilities

This contract is intended for the mobile app sync layer and should be treated as the source of truth for backend sync integration.

---

## Sync Model Overview

InspectPlus uses a pull/push sync model.

### Pull
The mobile app calls:

```ts
pull_changes(last_pulled_at: number)
```

The backend returns:
- changed rows grouped by entity
- a server timestamp to store as the next `last_pulled_at`

### Push
The mobile app calls:

```ts
push_changes(changes: object)
```

The backend receives:
- created rows
- updated rows
- deleted row IDs

## Pull Changes Contract

## Function

```ts
pull_changes(last_pulled_at: number)
```

### Input

- `last_pulled_at`
  - integer
  - milliseconds since Unix epoch
  - use `0` for initial sync

### Output shape

```json
{
  "changes": {
    "<entity_name>": {
      "created": [],
      "updated": [],
      "deleted": []
    }
  },
  "timestamp": 0
}
```

### Notes

- `timestamp` is generated by the backend
- the client must store the returned `timestamp`
- the next pull must use the last stored `timestamp`

---

## Pull Response Structure by Entity

Each entity appears under `changes`.

Example:

```json
{
  "changes": {
    "establishments": {
      "created": [],
      "updated": [],
      "deleted": []
    },
    "inspection_reports": {
      "created": [],
      "updated": [],
      "deleted": []
    }
  },
  "timestamp": 1715000000000
}
```

---

## Pull Deletion Behavior

### Hard-delete entities
For most child entities, deleted rows are currently handled as hard deletes.

### Soft-delete entities
The following entities use soft delete:

- `inspection_reports`
- `survey_reports`

For these entities:

- active rows appear in `created`
- deleted row IDs appear in `deleted`
- rows with `deleted_at is not null` should not be treated as active rows on the client

## Push Changes Contract

## Function

```ts
push_changes(changes: object)
```

### Input shape

```json
{
  "<entity_name>": {
    "created": [],
    "updated": [],
    "deleted": []
  }
}
```

### Output shape

```json
{
  "status": "ok"
}
```

---

## Push Contract Rules

### `created`
Contains full row objects to insert.

### `updated`
Contains full row objects to update.

### `deleted`
Contains an array of IDs.

Example:

```json
{
  "inspection_reports": {
    "created": [],
    "updated": [],
    "deleted": ["rep-001", "rep-002"]
  }
}
```

## Conflict Handling

The current conflict strategy is:

- **last-write-wins using `updated_at`**

### Rule
An incoming update is applied only if its `updated_at` is newer than or equal to the stored row’s `updated_at`.

### Effect
If the client pushes a stale update:
- the backend ignores it
- the stored row remains unchanged

### Client requirement
The client must preserve and send the correct `updated_at` value for updated rows.

---

## Deletion Rules

## Soft delete
Used for:
- `inspection_reports`
- `survey_reports`

When deleted through sync:
- row remains in database
- `deleted_at` is set
- `updated_at` is updated
- future pulls return the ID in `deleted`

## Hard delete
Currently used for:
- `purpose_of_inspection`
- `compliance_air`
- `compliance_water`
- `compliance_hazwaste`
- `compliance_eia`
- `establishments` (current behavior unless changed later)

## Client Responsibilities

The mobile app must:

### 1. Store `last_pulled_at`
After every successful pull, store the returned `timestamp`.

### 2. Use `0` for first sync
Initial sync must call:

```ts
pull_changes(0)
```

### 3. Preserve backend IDs
The client must preserve:
- `estab_id`
- `report_id`
- `survey_id`
- `purpose_id`
- `compliance_id`

### 4. Send complete update payloads
Updated rows should include all required fields expected by the backend function.

### 5. Preserve `updated_at`
For conflict handling to work correctly, the client must send the row’s `updated_at`.

### 6. Handle deleted IDs correctly
If an entity appears in `deleted`, the client must mark/remove it from the local store according to local sync rules.

### 7. Respect parent-child relationships
Child entities must not be pushed unless their parent row exists locally and remotely.

Examples:
- `purpose_of_inspection.report_id` must reference an existing `inspection_reports.report_id`
- all `compliance_*` tables must reference an existing `inspection_reports.report_id`
